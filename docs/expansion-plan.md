## 技術選型

沿用 React／TypeScript／Vite／Tailwind 與 GitHub Pages；新增 Supabase Auth、PostgreSQL、Realtime，前端只增加必要的 Supabase client。此 SPA 不需要為了分帳另換 Next.js，也不需要申請 Vercel。若日後有必須使用伺服器的需求，再另行提出方案。

新帳務模組與舊行程保存分離：既有 localStorage key、IndexedDB 及 v1 備份相容性保留，登入／登出不得重設行程、清單或照片。共同帳務只以雲端資料庫為準，不以 localStorage 取代雲端。切換帳號或旅程時清除畫面上的帳務快取，避免看到上一位使用者的帳務。

建議分層：`features/expenses/domain/` 放純計算與驗證，`data/` 放 Supabase 存取及即時訂閱，`components/` 放畫面；`supabase/migrations/` 放版本化資料庫、RLS 與 RPC。這些目錄目前尚未實作。

## 階段 1：雙人分帳

### 身分與邀請

- Email magic link 登入與顯示名稱；以 user UUID 關聯，不用顯示名稱當主鍵，也不給建立者預設 A 身分。
- 適當加入 Email 驗證碼替代入口，以處理 iPhone Email App 開到不同瀏覽器、PKCE verifier 不在該瀏覽器的情況。
- 登入回呼先於既有 Hash 路由處理；使用現有 Pages 根路徑的 `?code`，登入後清除回呼參數並轉到分帳頁，避免 `/auth/callback` 在靜態站點 404。
- 每趟最多兩名真實成員；只有一人時顯示邀請狀態，不建立假旅伴或假帳號。
- 邀請使用高強度隨機碼，伺服器只存雜湊；建議預設 24 小時到期、單次使用及可撤銷。
- 兌換邀請在資料庫交易內鎖定旅程與邀請，檢查登入身分、有效期限、未使用狀態與兩人成員上限，防止同時兌換加入第三人。

### 資料模型與權限

預計資料表：`profiles`、`trips`、`trip_members`、`trip_invites`、`expenses`、`expense_shares`、`settlements`、`mutation_requests`。

- 每個帳務資料列有 `trip_id`，付款人及分攤對象必須為該趟真實成員，透過外鍵／伺服器驗證約束。
- 所有私有表啟用 RLS；未登入、非成員或改寫請求參數都不能取得或變更帳務。個人資料亦不能公開列出其他使用者。
- 成員判斷使用受控 helper，避免 membership RLS 自我遞迴。必要 RPC 限定 authenticated、固定 `search_path`、最小授權，並在資料庫再核對 `auth.uid()`。
- 受控寫入集中在交易式 RPC，不能以直接呼叫資料表繞過版本、邀請、分攤及冪等檢查。
- 前端只使用 Project URL 與 publishable key；不加入 service role key、資料庫密碼或其他私人憑證。

### 計算、結算與匯出

- 日圓以整數儲存，驗證安全範圍。匯率使用 PostgreSQL `numeric`，前端保留十進位字串，以定點／decimal 運算，最後才四捨五入成整數台幣。
- 兩人平均分攤：非付款人承擔 `floor(金額 / 2)`，付款人承擔剩餘金額；不因成員順序決定多出的 1 圓。
- 單人及自訂分攤總和必須恆等於原始金額，由前端與資料庫雙重驗證。
- 帳務先以 JPY 記錄，TWD 為依共同設定匯率計算的估算；未設定匯率時明示，不填入假匯率。
- 支援付款人／分類篩選、日期排序與支出增刪改；刪除需確認。
- 結算另存付款人、收款人、金額及日期，支援部分結算，不刪原支出、不把轉帳再算成消費。
- 結算後每人淨餘額＝實際付款－應負擔＋已付結算－已收結算。正值為應收，負值為應付。
- CSV 含支出、各自分攤與結算資訊，附 UTF-8 BOM、正確跳脫及試算表公式防護。
- 計算純函式與資料存取分離，涵蓋雙方付款、奇數日圓、自訂金額、修改刪除、部分／完整結算、decimal 匯率與 CSV 測試。

### 同步與失敗處理

- Realtime 作為變更通知，再透過成員權限重新抓取雲端快照；首次訂閱、重連及頁面回到前景皆同步最新狀態。
- 修改與刪除皆檢查版本，衝突提示重新載入／確認，不默默覆寫；共同匯率與結算也需要版本保護。
- 刪除建議以 tombstone 保留，透過受 RLS 保護的更新事件通知，避免依賴刪除事件中的敏感內容。
- 明顯離線提示並阻止送出，不建立離線佇列。登入過期、斷線、超時及寫入失敗均顯示實際結果。
- Loading 狀態防連點；同一操作失敗重送沿用同一 mutation ID。伺服器依唯一 ID、使用者及 payload hash 保存結果，避免已入帳但回應遺失後重複入帳。

## 帳號與環境準備（階段 1 前）

目前環境未提供 Supabase 設定，沒有可用的 Supabase／Vercel 連接工具。以下尚未替使用者完成：

1. 登入 [Supabase](https://supabase.com/)，建立專屬專案，選擇合適的亞洲區域；資料庫密碼自行安全保存，不貼在對話或程式內。
2. 在專案的 Connect／API 設定取得 Project URL 與前端 publishable key。介面名稱可能隨官方更新，屆時依實際畫面引導。
3. 在環境設定加入 `VITE_SUPABASE_URL`、`VITE_SUPABASE_PUBLISHABLE_KEY`。Vite 變數會打包進前端，所以只能放公開 client 設定；不得放 service role key。GitHub Pages 的正式建置也需要相同的公開設定。
4. Auth 的 Site URL 設為 `https://joyce097054-cloud.github.io/sendai-trip-planner/`，Redirect URL 加入同一路徑及實際開發測試位址，不用不必要的萬用字元。
5. 確認 Email 登入與實際寄信設定；兩人的信箱都要真正收到登入信。若專案預設寄信不適用，另設 SMTP，憑證只放 Supabase 的安全設定。
6. 確認階段 1 後，我會提供版本化 migration 與逐步套用方式，再設定 Realtime 表格。建立表格不等於 RLS 或同步已驗證。
7. 環境目前只有套件站點的出站規則；取得專案 ID 後，還需允許該專案的 HTTPS／Realtime 目的地，並另行測試實際連線。

不需要為此先建立 Vercel 帳號。只有真實兩帳號加入、收信、RLS、即時同步與重連測試成功，才會回報這些能力已完成；測試替身不算正式功能驗收。
